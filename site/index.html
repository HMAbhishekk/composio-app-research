The headline, in five findings

Read this section and you've got the whole study. Everything below is the evidence.

Auth

OAuth2 dominates, but it's the friction, not just the mechanism

71% of apps support OAuth2 and it's the single most common auth method — but OAuth2 is also where most of the "ready-with-friction" cases live, because publishing a multi-tenant OAuth app usually triggers a review step even when a single-workspace API key doesn't.

Self-serve

Two-thirds of apps hand a developer working credentials with zero human contact

65 of 100 apps are self-serve today (free signup → working API key, no sales call). Another 21% are "mixed" — self-serve for a single account, gated only when you want to publish a multi-tenant integration.

MCP coverage

MCP adoption is real but wildly uneven by category — and moving weekly

Developer/Infra tools are at 100% official MCP coverage; Ecommerce and Marketing sit at 20–30%. Our own verification pass caught 3 apps (ClickUp, Plaid, Otter AI) where an official MCP had shipped since the first research pass — this fact ages faster than almost anything else in the dataset.

The hard blockers

Only 5 of 100 apps are genuinely blocked — and it's always the same shape

DealCloud, Gladly, LinkedIn Ads, PitchBook, and (unconfirmed as a distinct product) "Paygent Connect." Every real block is an enterprise-sales relationship, not a technical one — no free trial, no self-serve signup, credentials only after a contract.

Where the easy wins are

Productivity/PM and Developer/Infra are the easiest categories, Finance and Marketing the hardest

Productivity tools (Notion, Linear, Asana, monday.com...) are 90% self-serve with 80%+ official MCP coverage — almost zero build cost. Finance/Fintech is the opposite: 40% gated or blocked, because money-moving APIs default to identity/compliance review.

Honest misses

3 apps stayed low-confidence even after two passes

Paygent Connect, iPayX, and higgsfield are small/obscure enough that neither research pass could fully pin down their public documentation. We report that directly rather than guessing — see the Verification section for exactly what's uncertain and why.

The agent: what we built

This is not a script that fills in a spreadsheet from memory. It's an agentic research pipeline with a forced structured-output contract, and a second, adversarial agent whose only job is to try to prove the first one wrong.

1

Fan out — 10 category agents

One Claude subagent per category (10 apps each), each given the exact 10-field schema and instructed to WebSearch and WebFetch real docs, not answer from memory. Runs in parallel.

→
2

Aggregate — 100-row dataset

All 10 batches merged and schema-validated (id coverage, no dupes) into one dataset: results_pass1.json.

→
3

Verify — 4 adversarial agents

A stratified 20-app sample, re-checked by separate agents instructed to try to refute the original claim against primary sources — not reproduce the research.

→
4

Correct — human-applied patch

Every confirmed error was patched into results_final.json with an audit trail (what changed, why, source URL) — see Verification below.

What the agent did end-to-end

  • Searched and read real developer docs for all 100 apps (not just the hinted URL — several agents had to search past a dead/redirected hint, e.g. fanbasis → Commas).
  • Extracted auth method(s), self-serve vs gated status with a one-sentence evidence rationale, API surface breadth, and existing-MCP status with the specific repo/package name.
  • Assigned a buildability verdict and, where blocked, named the specific blocker rather than a generic "gated."
  • Self-reported a confidence level per app, and used it honestly — 3 apps stayed "low confidence" rather than being guessed into a false-precision answer.
  • Cited an evidence URL per app, so every claim on this page traces back to a specific doc page.

Where a human was needed

  • Scoping the schema — deciding what "self-serve" vs "gated" vs "mixed" actually means precisely enough for an agent to apply consistently across 100 very different apps.
  • Picking the verification sample — a stratified 20-app sample (2 per category, biased toward low/medium-confidence and surprising claims) rather than a random sample, so the check would actually stress-test the weak points.
  • Judging close calls — e.g. deciding that Otter AI's Enterprise-only REST API still counts as "self-serve" (an Enterprise admin can self-serve a key, even though not every user can), a policy call the agent can't make on its own.
  • Applying the corrections — the verification agents surfaced 9 fixes; a human (this pipeline's code) applied each one as a tracked patch with a stated reason, rather than silently overwriting the original.
  • Building this page — turning 100 rows and a verification log into something a reviewer can actually understand in two minutes.

Where the agent got it wrong (stated plainly, as asked)

ClickUp and Plaid: pass-1 said "no official MCP server exists" for both. Both are wrong today — ClickUp shipped an official first-party MCP server (mcp.clickup.com/mcp, OAuth 2.1, public beta), and Plaid's own GitHub org publishes one (plaid/ai-coding-toolkit). This is the single biggest lesson from this project: MCP-existence claims go stale faster than almost any other fact here, because new official servers ship weekly. A production version of this pipeline needs a recurring MCP-freshness re-check, not a one-time snapshot.

Otter AI: pass-1 concluded "no public API key access, MCP-only" based on an Otter help-center statement that turned out to be outdated — Otter now documents a full Enterprise-tier REST API with Bearer-token keys. Corrected to self-serve / ready-now.

Sherlock's community MCP claim and fanbasis/Commas' confidence level were both adjusted in the opposite direction — one downgraded (a claimed MCP wrapper couldn't be re-confirmed), one upgraded (the "inaccessible" API docs turned out to be a real, named, publicly reachable API reference page that pass-1 was too quick to give up on).

Three apps remain genuinely low-confidence even after two passes: Paygent Connect (could not confirm it exists as a distinct product from the "Paygent" UK merchant-services brand or NMI's gateway), iPayX (real but extremely early-stage — a single-commit GitHub repo), and higgsfield (real product, but documentation too thin/scattered to fully verify pricing, rate limits, or a formal API reference). These are reported as low-confidence rather than resolved one way or the other, because that's what the evidence actually supports.
